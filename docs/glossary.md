## 1. 결제 프로세스 용어

### Payment (결제)

결제 요청을 받아 카드사/은행에 승인을 요청하는 단계.

```
고객 → 가맹점 → PG사 → 카드사 → 승인/거절
```

**관련 개념:**

- Authorization (승인): 카드사가 결제 가능 여부를 확인하고 승인하는 것
- Capture (매입): 승인된 거래를 실제로 처리 요청하는 것

---

### Clearing (청산)

결제 완료 건들을 집계하고 정산 금액을 계산하는 단계.

**주요 활동:**

- 일별 거래 집계
- 수수료 계산
- 정산 금액 산출

```
승인 완료된 거래들 → 집계 → 수수료 공제 → 정산 금액 확정
```

---

### Settlement (정산)

실제 자금 이체가 발생하는 최종 단계.

**정산 주기 예시:**
| 구분 | 정산 주기 | 설명 |
|------|----------|------|
| D+0 | 당일 정산 | 거래 당일 정산 (수수료 높음) |
| D+1 | 익일 정산 | 거래 다음 영업일 정산 |
| D+3 | 3영업일 정산 | 일반적인 신용카드 정산 |

---

### Reconciliation (대사)

내부 거래 기록과 외부 기록(은행, 카드사)을 비교하여 불일치를 찾는 과정.

**대사 유형:**
| 유형 | 설명 |
|------|------|
| 정상 매칭 | 내부/외부 기록 일치 |
| 불일치 | 금액 또는 건수 차이 발생 |
| 미매칭 | 한쪽에만 기록 존재 |

```
내부 거래 기록 ←→ 은행 입금 내역
       ↓
   차이 분석
       ↓
  수동 조정 또는 자동 처리
```

---

### Chargeback (지불 거절)

카드 소유자가 거래를 분쟁(dispute)하여 카드사가 가맹점에게 금액을 환수하는 것.

**Chargeback 사유:**

- 사기 거래 (Fraud)
- 상품 미수령
- 중복 청구
- 서비스 불만족

---

## 2. 정산 관련 용어

### 수수료 (Fee) 구조

```
거래 금액 (Transaction Amount)
    └─ PG 수수료 (PG Fee): 2~3%
         └─ 카드사 수수료 (Card Fee): ~1.5%
              └─ VAN 수수료 (VAN Fee): ~0.1%
```

| 수수료 유형   | 부과 주체  | 대략적 비율 |
| ------------- | ---------- | ----------- |
| PG 수수료     | 결제대행사 | 2.0~3.5%    |
| 카드사 수수료 | 카드사     | 1.0~2.0%    |
| VAN 수수료    | VAN사      | 0.05~0.15%  |

---

### 정산금 계산

```
정산금 = 거래 금액 - 수수료 - 부가세
```

**예시:**

```
거래 금액: 100,000원
PG 수수료: 3% = 3,000원
부가세 (수수료의 10%): 300원
─────────────────────
정산금: 96,700원
```

---

### 역정산 (Reverse Settlement)

이미 정산 완료된 건에 대해 환불이 발생했을 때, 다음 정산에서 차감하는 것.

```
[정산 완료]
    ↓
[환불 요청]
    ↓
[다음 정산에서 차감]

예시:
  당일 정산 예정: 1,000,000원
  역정산 금액: -50,000원 (전일 환불건)
  ─────────────────────────
  실제 정산금: 950,000원
```

## 3. 트랜잭션 관련 용어

### Idempotency (멱등성)

동일한 요청을 여러 번 보내도 결과가 같음을 보장하는 특성.

**결제에서의 중요성:**

- 네트워크 오류로 재시도 시 중복 결제 방지
- 클라이언트가 안전하게 재시도 가능

**구현 방식:**

```
POST /payments
Headers:
  Idempotency-Key: "unique-request-id-123"

→ 같은 Key로 재요청 시 기존 결과 반환
```

---

### Optimistic Locking (낙관적 잠금)

충돌이 드물다고 가정하고, 커밋 시점에 충돌을 감지하는 방식.

```java
@Entity
public class Payment {
    @Version
    private Long version;  // 자동 증가
}

// 동시 수정 시 OptimisticLockException 발생
```

**적합한 경우:** 읽기가 많고 쓰기 충돌이 드문 경우

---

### Pessimistic Locking (비관적 잠금)

충돌이 발생할 것이라 가정하고, 미리 잠금을 획득하는 방식.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<Payment> findByIdForUpdate(Long id);
```

**적합한 경우:** 쓰기가 빈번하고 충돌이 예상되는 경우

---

### Distributed Lock (분산 잠금)

여러 서버 인스턴스에서 동시 접근을 제어하기 위한 잠금.

```
Redis (Redisson)를 이용한 분산 락:

Server A ─┬─→ [Redis Lock] ─→ 획득 성공 → 처리
Server B ─┘         ↓
                 대기/재시도
```

---

### Two-Phase Commit (2PC)

분산 트랜잭션에서 일관성을 보장하기 위한 프로토콜.

```
Phase 1: Prepare (준비)
  Coordinator → 모든 Participant: "커밋 가능?"
  모든 Participant → Coordinator: "Yes/No"

Phase 2: Commit (커밋)
  모든 Yes → 커밋 명령
  하나라도 No → 롤백 명령
```

---

### Saga Pattern

분산 시스템에서 로컬 트랜잭션의 연속으로 일관성을 유지하는 패턴.

```
[주문] → [결제] → [재고 감소] → [배송]
   ↓        ↓          ↓
 실패 시 보상 트랜잭션 (Compensation)

[주문 취소] ← [결제 취소] ← [재고 복구]
```

## 4. 보안/컴플라이언스 용어

### PCI-DSS

Payment Card Industry Data Security Standard. 카드 정보 보안 표준.

**주요 요구사항:**

| 요구사항        | 설명                 |
| --------------- | -------------------- |
| 카드번호 암호화 | AES-256 이상         |
| CVV 저장 금지   | 인증 후 즉시 폐기    |
| 접근 제어       | 최소 권한 원칙       |
| 로그 기록       | 모든 접근 기록       |
| 네트워크 보안   | 방화벽, 세그먼테이션 |

---

### Tokenization (토큰화)

민감한 데이터(카드번호)를 무의미한 토큰으로 대체하는 것.

```
실제 카드번호: 4111-1111-1111-1111
        ↓ 토큰화
토큰: tok_a1b2c3d4e5f6

→ 토큰은 의미 없는 값, 원본은 안전한 금고(Vault)에 저장
```

---

### Masking (마스킹)

민감 데이터의 일부를 가려 표시하는 것.

```
카드번호: 4111-****-****-1111
계좌번호: ***-**-123456
이메일: h***@example.com
```

---

### HSM (Hardware Security Module)

암호화 키를 안전하게 저장하고 관리하는 전용 하드웨어.

**용도:**

- 암호화 키 생성/저장
- 암호화/복호화 연산
- 디지털 서명

---

## 5. 시스템 아키텍처 용어

### PG (Payment Gateway)

결제대행사. 가맹점과 카드사/은행을 연결하는 중개자.

```
가맹점 → PG사 → VAN사 → 카드사
              ↘ 간편결제
               ↘ 계좌이체
```

**국내 주요 PG사:** 토스페이먼츠, NHN KCP, 나이스페이, 이니시스

---

### VAN (Value Added Network)

카드 승인 전문을 중계하는 부가가치통신망 사업자.

```
PG사 → VAN사 → 카드사
       (전문 중계)
```

---

### 전문 (Transaction Message)

금융 기관 간 데이터 교환을 위한 표준화된 메시지 형식.

**ISO 8583 예시:**

```
MTI (Message Type Indicator): 0200 (승인 요청)
Primary Account Number: 4111111111111111
Processing Code: 000000
Amount: 000000010000 (100.00)
...
```

---

### Circuit Breaker (회로 차단기)

외부 시스템 장애 시 빠른 실패를 통해 시스템을 보호하는 패턴.

```
상태:
  CLOSED → 정상 동작, 요청 통과
  OPEN → 장애 감지, 즉시 실패 반환
  HALF_OPEN → 일부 요청으로 복구 확인

[정상] → 오류 임계치 초과 → [OPEN]
                              ↓ (타임아웃)
                          [HALF_OPEN]
                              ↓ (성공)
                            [CLOSED]
```

---

### Retry with Exponential Backoff

실패 시 점점 더 긴 간격으로 재시도하는 패턴.

```
1차 시도 실패 → 1초 후 재시도
2차 시도 실패 → 2초 후 재시도
3차 시도 실패 → 4초 후 재시도
4차 시도 실패 → 8초 후 재시도
... (최대 재시도 횟수까지)
```

## 6. 카드 결제 관련 용어

### BIN (Bank Identification Number)

카드번호 앞 6자리로, 발급 기관을 식별.

```
4111 11XX XXXX XXXX
└──┘
BIN (Visa 카드)

BIN 범위:
  4XXX: Visa
  51-55: Mastercard
  34, 37: American Express
  62: UnionPay
```

---

### CVV/CVC

Card Verification Value. 카드 뒷면 3자리 보안 코드.

**보안 규칙:**

- 승인 요청 시에만 사용
- 저장 절대 금지 (PCI-DSS 위반)
- 로그에 기록 금지

---

### 무승인 거래 vs 승인 거래

| 구분      | 무승인 거래        | 승인 거래 |
| --------- | ------------------ | --------- |
| 승인 단계 | 생략               | 필수      |
| 예시      | 정기결제, 소액결제 | 일반 결제 |
| 리스크    | 높음               | 낮음      |

---

### 망취소

네트워크 오류 등으로 승인 완료 후 응답을 못 받았을 때, 일정 시간 후 자동 취소하는 것.

```
[승인 요청] → [카드사: 승인 완료]
     ↓
[응답 타임아웃] → 클라이언트: 실패로 인식
     ↓
[5분 후 망취소 실행] → 카드사에 취소 요청
```
